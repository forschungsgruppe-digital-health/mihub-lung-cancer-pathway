# Contributing

Thank you for helping improve the MiHUB lung-cancer patient-pathway models. This guide
covers how to edit the models, run the checks, and propose a change. The modelling
rules themselves live in [`CONVENTIONS.md`](CONVENTIONS.md); the acceptance-test criteria in
[`docs/governance/`](docs/governance/). Please also read the
[`DISCLAIMER.md`](DISCLAIMER.md) and the [Code of Conduct](CODE_OF_CONDUCT.md).

## Before anything else

- **No real patient data.** Use only synthetic / abstract content. Never commit
  real patient data — not even realistic-looking data.
- **Not for clinical use.** These are research/reference models; do not weaken the
  intended-use disclaimer.

## Modeller workflow

The models are changed **by humans only** — AI agents never edit, move or re-export
`.bpmn`/`.svg` files; they report findings instead (see [`AI_USAGE.md`](AI_USAGE.md)). A model
change goes through these steps:

1. **Branch off `dev`** (e.g. `git switch -c feat/screening-… dev`).
2. **Open the `.bpmn` in a bpmn-js-based editor** — [demo.bpmn.io](https://demo.bpmn.io/)
   (no install), the [Camunda Modeler](https://camunda.com/download/modeler/) (desktop) or the
   Camunda Web Modeler; these are the exporters recorded in `models/*.bpmn`. Do not hand-edit
   the XML.
3. **Model per [`CONVENTIONS.md`](CONVENTIONS.md):** verb-object labels, **no OR-gateways**
   (use XOR/AND), one start / named end event(s) per level, decompose levels > ~50 elements
   via Call Activities, declared conformance class **Analytic** (see
   [ADR-0001](docs/decisions/0001-repo-tooling-and-conformance-gate.md)).
4. **Serialisation rules** — what the gate and the moddle roundtrip depend on:
   - keep the `bpmn:` namespace prefix the editor writes; some older models are still
     un-prefixed — do not re-prefix a model you are not otherwise changing *(modellers to
     confirm)*;
   - give the `<process id="…">` a meaningful, stable id (e.g. `Process_lung_cancer_screening`
     rather than the editor's random `Process_0bdppus`) and never change it afterwards — it is
     the Call-Activity target *(modellers to confirm the pattern)*;
   - no manual line breaks in labels — let the editor wrap;
   - leave the `cp:` quality indicators (BPMN4CP) exactly as they are: they sit directly under
     the process by design, and the roundtrip preserves them losslessly;
   - the `i18n:` translation layer is optional — keep it only if you maintain it in the same
     change (a stale translation is worse than none).
5. **Re-export the matching `.svg`** — "Download as SVG" in the same editor, same basename
   (`models/lung-cancer-<phase>-pathway.svg`) — after **every** model change. The `.bpmn` is the
   source of truth; the `.svg` must not drift.
6. **Run the gates** — `npm run check:conformance` and `npm run check:soundness` (see
   [Running the checks](#running-the-checks)).
7. **Commit model + svg together** with a Conventional Commit whose scope is the phase:
   `feat(screening): …` / `fix(aftercare): …` (`!` for a structural/semantic change, see below).
8. **Open the PR from your working branch into `dev`.** Reference the model's GitHub issue
   (label `model`) in the PR description — that issue is updated from the gate run on the PR.

## Running the checks

Prerequisites: Node ≥ 22 (`.nvmrc`; CI uses 22 — with nvm: `nvm use`). Install once, then run the gate:

```bash
npm ci
npm run check:conformance     # naming + bpmnlint + model metrics + roundtrip + XSD core
npm run check:soundness       # STR-1…4 behavioural soundness (advisory; needs the analyzer container — see skills/bpmn-soundness/SKILL.md, ADR-0003)
npm run abnahme:protokoll     # pre-fills an acceptance-test Protokoll with the A-check evidence (exits 1 while any A-check is red)
```

The decision lives in the tools, not in the model. The gate runs its layers in this
order — **blocking:** model naming ([ADR-0004](docs/decisions/0004-repo-structure-and-model-naming.md):
`models/lung-cancer-<phase>-pathway.{bpmn,svg}`, paired), bpmnlint (structure), the
no-OR model-metrics check (Abnahmetest SYN-5; SYN-2/SYN-4 advisory) and the moddle
roundtrip (stable serialization + lossless `cp:` BPMN4CP extension content; `i18n:`
attributes pass through); **informational:** XSD core (OMG BPMN20.xsd). The XSD layer
validates a *core view* of each model (`tools/xsd-core-view.mjs`): the BPMN4CP `cp:`
elements are excluded first — `cp:qualityIndicator` is a direct child of the process **by
design** and is validated by the moddle layer; `i18n:` content sits in `extensionElements`
(lax) — so an XSD failure is a genuine BPMN-core deviation. Today only the overarching
model's un-namespaced DI colour attributes remain (informational, housekeeping) — see
[`docs/model-issues/2026-09-04-xsd-core-extension-placement.md`](docs/model-issues/2026-09-04-xsd-core-extension-placement.md)
(resolved: by design).
Every layer is also runnable on its own (`npm run check:naming`, `lint:bpmn`,
`check:metrics`, `check:roundtrip`, `check:xsd`). See
[`skills/bpmn-conformance/SKILL.md`](skills/bpmn-conformance/SKILL.md) for how to read the
output (element references print as `"Name" (id)` or `‹unnamed Type› (id)`). The soundness
check classifies each model SOUND / VIOLATION / INCONCLUSIVE / ERROR — INCONCLUSIVE and ERROR
are never a pass ([ADR-0003](docs/decisions/0003-soundness-tooling.md)).

> In CI the conformance **aggregator** currently runs **advisory (warn-only) on the existing models by design**
> (pre-existing structural defects + OR-gateways): it **reports** the findings as warnings but does
> **not** fail the check or block PRs — the local default stays strict, and hard enforcement is
> re-enabled after the planned remodel. The **naming convention** is the exception: it is enforced
> as its own **blocking** CI step. See [`docs/decisions/0001`](docs/decisions/0001-repo-tooling-and-conformance-gate.md).
> When you touch a model, aim to leave it no worse; the planned remodel will green the strict gate.

## Commits, branches, and pull requests

- **Conventional Commits**, scope = the pathway file:
  `feat(treatment)!: replace OR-gateway with XOR`, `docs(governance): …`,
  `fix(aftercare): add missing end event`. A `!` (or `BREAKING CHANGE:`) marks a change
  that alters the pathway's structure/semantics (see the versioning policy in
  [`docs/decisions/0002`](docs/decisions/0002-versioning-and-release.md)).
- **Branch off `dev`** and open a **pull request into `dev`** (`gh pr create --base dev`).
  `dev` is the active-development branch; `main` is for **releases**. Do **not** push
  directly to `dev`/`main`, and never `git push origin dev:main`. Promotion is a
  separate `dev` → `main` PR.
- **One logical change per PR**; keep diffs reviewable. A human reviews and merges —
  please don't self-merge. The PR template lists the checks to confirm.
- **Commit with an e-mail address that is verified on your GitHub account** — your
  `@tu-dresden.de` address or GitHub's noreply address
  (`<id>+<login>@users.noreply.github.com`); set it once per clone with
  `git config user.email …`. Machine-generated addresses (`user@hostname.local`) and personal
  addresses end up permanently public in the history and cannot be removed later —
  `.mailmap` only consolidates how they are *displayed*.
- **Cutting a release candidate** (maintainers): put a one-time footer
  `Release-As: X.Y.Z-rc.N` (e.g. `Release-As: 0.4.0-rc.1`) on a real, releasable commit in a
  PR into `dev` (`version:` and `date-released:` in `CITATION.cff` are rewritten by
  release-please via the `# x-release-please-version` / `# x-release-please-date` markers —
  do not hand-edit them); promote `dev` → `main` by PR. release-please then opens
  `chore(main): release X.Y.Z-rc.N` on `main`; merging it tags `vX.Y.Z-rc.N`, publishes a
  GitHub pre-release and triggers the Zenodo deposit (metadata from `.zenodo.json`). Never
  pin `release-as` in `release-please-config.json` — a pin is sticky and ends in a
  duplicate-tag failure ([ADR-0002](docs/decisions/0002-versioning-and-release.md)).
- **After every release:** merge `main` back into `dev` (PR) so that `version.txt`,
  `.release-please-manifest.json`, `CHANGELOG.md` and `CITATION.cff` stay in sync on `dev`.
  Without it the next feature PR from `dev` re-diverges the release bookkeeping.

## Review & acceptance test

Routine PRs get a peer review against [`CONVENTIONS.md`](CONVENTIONS.md) §8.1 and the
conformance gate. A **formal acceptance test** ("Abnahmetest") of a pathway additionally runs
the [governance instrument](docs/governance/): a technical gate (tools), a clinical
gate (expert consensus), and a pragmatic gate (joint walkthrough), recorded in a
signed Protokoll. Tools prepare evidence; humans decide.

## Reporting issues

Report bugs, model defects, and change requests via the repository's **GitHub issue tracker**
(the *Issues* tab): <https://github.com/forschungsgruppe-digital-health/mihub-lung-cancer-pathway/issues>.

- **Model defects / change requests** use the **BPMN model issue** template (bilingual DE + EN;
  labels `model`, `needs-clinical-review`). For BPMN-XML problems surfaced by a tool or agent,
  see [`docs/model-issues/`](docs/model-issues/): tools/agents record findings there (they never
  edit a model), and a human files the issue from that finding.
- **Anything else** — a question, a documentation gap, repo hygiene — goes in a **blank issue**
  with the matching label: `question`, `documentation` or `housekeeping`.
- The template chooser ([`.github/ISSUE_TEMPLATE/config.yml`](.github/ISSUE_TEMPLATE/config.yml))
  also links **GitHub Discussions** for open-ended questions and the **security contact**
  ([`SECURITY.md`](SECURITY.md)) for anything that should not be public.

## AI-assisted contributions

This repository uses AI coding agents for tooling, documentation and audits — never for the
models. The full disclosure (EU AI Act Art. 50, COPE) is [`AI_USAGE.md`](AI_USAGE.md). Rules for
contributors:

- **Models are human-only.** No AI tool may edit, move or re-export `.bpmn`/`.svg` files; agents
  report findings (`docs/model-issues/`, GitHub issues) and a human modeller changes the model.
- **Mark AI-assisted commits** with a trailer naming the tool and model, e.g.
  `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>` (Claude Code sets it automatically;
  other tools use the same trailer with their own name). AI-drafted PRs and issues end with a
  "🤖 Generated with …" footer.
- **Tick the disclosure box** in the pull-request template and review AI output before you
  submit it — the human author of the PR is responsible for its content.
- **Update `AI_USAGE.md`** when a new tool, model version or AI-assisted artifact class appears.
